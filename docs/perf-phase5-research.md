## Critic (all corrections applied)
1. **The roll-up does not follow from the plan's own lever table.** Probability-weighted removal = 2.6(.85) + 0.8(.50) + 0.4(.40) + ~0.33-0.6(D at 30%) − 0.4 overlap = **~2.6-2.7 cpu-s**, landing at **~31.0-31.1 cpu-s → ~44 steady-state / ~37.5 wall**, not the claimed "3.9-4.4 removed → 29.5-30 cpu-s → 44-46 / 38-39." The internal mapping is also inconsistent (29.5-30 cpu-s would give 46-46.5 steady, not 44-46). "P(29.5-30.5 cpu-s) ~60%, the committed outcome" requires roughly A+B+D all landing, which the table's own P column prices nearer 30-40%. Either the P(lands) column or the committed outcome is wrong; the defensible commit at these numbers is 42-44 steady-state / ~37 wall.

2. **WS-A's "2.6 floor at 85%" contradicts the per-cell profile and must be reconciled before booking.** osm_fetch+parse = 946+646 = 1.59 cpu-s uncontended = ~3.2-3.5 contended (at the 2.04-2.07x uniform inflation). The 441 cpu-s/run figure implies 5.4 cpu-s/cell — 1.6x more than the marks allow — and the plan's own residual target (≤170 cpu-s/run = 2.1/cell) already exceeds the entire marked phase. The sidecar also retains bincode decode + per-read JSON re-hash. If the marks are right, 2.6 is ~75-80% of the whole contended phase — not a floor — and the true floor is ~1.5-2 cpu-s, which drops every downstream cumulative cell by ~1. A1/A6 must explicitly reconcile 441-vs-marks (halo tiles? decode outside the osm_fetch mark?) and the 85% booking is unsupported until they do.

3. **D1(b) is not "pure correctness" and is mis-GO'd at 90%.** Adding the missing flushed_regions check to insert_block_entity changes default output in every world where the resurrect-after-flush hole currently fires — a default-byte-identity violation shipped unconditionally. Worse, if ARNIS_BLOCK_HASH does not cover block-entity NBT, G1 is blind to it in both directions. Required before landing: (a) confirm block entities are inside the hash currency; (b) a corpus run proving the hole never fires today (hash-equal with/without the check); or (c) split D1(b) out of the unconditional batch behind its own flag. D1(a) alone keeps the 90%.

4. **Unfunded ship-blocker: the Meld-side gate.** The flag's ship condition is "Meld enables it only behind its own permanent per-cell canonical-hash regression gate," but no task, files, or hours exist for building it — D2 scopes only arnis files, and Meld's consumption of ARNIS_BLOCK_HASH_CANONICAL (prefetch/驱动 plumbing, gate storage, failure handling) is nowhere in the 74h. Same gap, smaller: A4's Meld plumbing is priced but D's is not. Add a scoped WS-D task or the flag can never ship even if D3-D5 all pass.

5. **Codec-drift hole in G2: bincode itself is unpinned.** G2 bumps OSM_SIDECAR_CODEC_VERSION on serde-*shape* changes and G5 pins zstd/miniz_oxide, but a bincode crate or config bump changes wire bytes with zero shape change; bincode is not self-describing, so an old sidecar under a new bincode either fails open (fine) or misdecodes *silently* (fleet-wide wrong worlds, invisible to verify-at-bake, which only ever ran under the old binary). Add bincode to the output-affecting pin list and mandate a codec-version bump on any bincode upgrade. Also: the verify-at-bake element compare must be bit-wise on f64 (PartialEq gives NaN≠NaN false-fails and -0.0==0.0 false-passes), matching A2's own roundtrip-test standard.

6. **Two things the benchmark as protocoled cannot measure.** (a) "Cold-run regression <1%": a truly cold run includes network fetch whose variance dwarfs 1%; define cold as JSON-warm/sidecar-absent or the gate is unevaluable. (b) The contended first-run bake path is never exercised anywhere: A6 pre-bakes sidecars, so N=16 concurrent first-writer-wins renames — on Windows, where rename-over-open-destination fails — go untested; a persistent rename-failure loop would silently mean sidecars never persist in production while every bench passes. Add one N=16 sidecar-cold (JSON-warm) run to A5/A6.

Nits: (i) WS-E's task id "E1" collides with the experiment labels E1/E2/E3 used inside WS-A and WS-D rows — gate references like "requires E1 tokenizer dominance" are ambiguous on paper. (ii) D's 0.8-1.5 bracket is stated as a subset of the *uncontended* 2.94, violating the state-against-contended rule (conservative direction, but the rule admits no direction). (iii) Meld's cache TTL/cleanup lifecycle never learns about .osmbin — orphaned sidecars accumulate after JSON prune/re-download, roughly doubling OSM cache footprint with no reaper.

## 0. Storage model and what one set_block costs

**Data structure hierarchy** (src/world_editor/common.rs):
- `WorldToModify` = `FnvHashMap<(i32,i32), RegionToModify>` keyed by region (common.rs:610-612)
- `RegionToModify` = `FnvHashMap<(i32,i32), ChunkToModify>` keyed by region-local chunk (common.rs:592-594)
- `ChunkToModify` = `FnvHashMap<i8, SectionToModify>` + `other: FnvHashMap<String, Value>` for block_entities/fluid_ticks (common.rs:546-549)
- `SectionToModify` = `BlockStorage` + `properties: FnvHashMap<usize, Arc<Value>>` (common.rs:283-287)
- `BlockStorage` enum: `Uniform(Block)` (no heap), `Full(Vec<u8>)` = 4096 B heap, `FullWide(Vec<Block>)` = 8192 B heap (`Block` is a `u16` newtype, block_definitions.rs:60-64) (common.rs:151-158)

**The dominant write path** (`None`/`None` whitelist, explicitly fast-pathed at mod.rs:1450-1455):
`WorldEditor::set_block` (mod.rs:1378) → bbox check (:1393) → `get_absolute_y` = `get_ground_level` (road-override FNV lookup + bilinear elevation, mod.rs:687, 703) → `set_block_with_properties_absolute` (mod.rs:1431): second bbox check (:1441), flushed-regions guard `is_empty() + FnvHashSet contains((x>>9, z>>9))` (:1445) → `WorldToModify::set_with_props_if_absent` (common.rs:773): **three FNV hashmap entry ops** — region `(x>>4)>>5` key (common.rs:790-793), chunk `(chunk_x&31, chunk_z&31)`, section `i8` — then YZX index (common.rs:334-336), `storage.get(idx)` AIR test, `storage.set(idx)` (promotes `Uniform`→`Full` with a 4096 B `vec!` alloc on the first differing write in a section, common.rs:181-190), plus a `properties` map insert/remove per call (common.rs:800-805). So per call: ~4-5 FNV hash probes, 1 elevation lookup (relative-Y form only), occasional 4 KiB allocation. Whitelist/blacklist calls pay an extra full `get_block` descent first (mod.rs:1457).

**Region key computation sites**: `x >> 9` at every editor guard (mod.rs:904, 1101, 1445, 1614, 1667); `(x>>4)>>5` inside every `WorldToModify` descent (common.rs:684-687, 790-793, 826-829, 872-874); `min_x >> 9` per tile (data_processing.rs:648-649); `div_euclid(512)` in save (java.rs:166-169); `region_is_canonical` (mod.rs:317-324).

## 1. Keep-rectangle check at set_block level

**Yes, mechanically trivial.** The rectangle already exists process-globally: `region_keep::set` from `args.canonical_regions` (data_processing.rs:325, args.rs:191), `is_kept(rx,rz)` = OnceLock get + 4 i32 compares (mod.rs:297-307). Today it fires only at flush (`flush_region_via`, mod.rs:648-655) and final save (java.rs:184, 220-222).

**Cost per call**: 2 shifts + one OnceLock acquire-load + 4 compares, ~1-3 ns — noise next to the 4-5 hash probes already paid. Cheaper still: cache the rect as a plain `Option<(i32,i32,i32,i32)>` field on `WorldEditor` at construction, or **pre-seed `flushed_regions` with the never-kept region keys** at editor construction — then every existing guard site drops the writes with zero new branches (cost: the `is_empty()` fast-path is lost, one FNV probe per call; and the flushed/skipped accounting in `region_stats` and `flush_region_via` semantics would need care since `flushed_regions.insert` is also done there, mod.rs:652, 658).

**Single cheapest place**: extend the existing helper `is_region_flushed(x,z)` (mod.rs:1100-1102) into "flushed OR not kept" — it and its five sibling inline guards (mod.rs:904, 1445, 1614, 1667, plus is_region_flushed's callers at 1178, 1264, 1341, 1117) already compute `(x>>9, z>>9)`. Additionally check early in `set_block` itself (right after mod.rs:1393), because the relative-Y form pays the **elevation lookup before** reaching the absolute-path guard — the region key needs only x,z, so a front check also skips `get_ground_level` for halo writes.

**Caveat on the win**: a set_block guard saves only the storage-side cost (hash descents, section allocs, later merge/hash work), not the upstream geometry/element math that produced the call. It is therefore a strict subset of the 2.94 cpu-s/cell halo cost; how big a subset **cannot be told without an experiment** (E3 below).

## 3. RAM a halo region occupies before eviction

Structure per resident chunk: chunk-map entry + section-map entries + per-section `BlockStorage` (0 B heap if `Uniform` — the fillground bulk fill leaves buried sections `Uniform(STONE)`, common.rs:896-903; 4096 B `Full` for any mixed section — caves carving, surface strata, water-depth carve all promote; 8192 B `FullWide` for sections containing id ≥ 256) + a properties map. `compact_sections`/`try_compact` can collapse back to Uniform (common.rs:222-243, 1305-1316) but only run on flush/save paths.

**Derived numbers** (labelled derived): a cs4 cell's halo is a 128-block strip (2304−2048)/2 around 16 canonical regions → 20 halo regions = 16 edge (8×32 = 256 chunks each) + 4 corner (8×8 = 64 chunks) ≈ **4 352 halo chunks**. The codebase's own calibration is **~26 MB resident per region** on a dense full-feature run (data_processing.rs:290-292, measured by the authors); halo regions hold only a quarter-strip (edge) or 1/16 (corner) of a full region → derived ≈ 16×6.5 MB + 4×1.6 MB ≈ **110 MB/cell**, with wide error bars (caves/fillground swing per-chunk cost several×). At N=16 concurrent cells that is derived ~1.7 GB of the 31.4 GB machine — plausibly part of the memory-bandwidth contention story, but the honest answer is measure it (E2). Note under active eviction, halo regions are already dropped un-serialized at their flush point (mod.rs:648-655); the write-time guard only moves the free **earlier** (write time vs. owner+8-neighbors-merged time) and keeps them out of the tile editors too.

## 4. THE CORRECTNESS QUESTION — every read-back path

**One strong safe claim first**: the tile merge **cannot** move a dropped halo write into a canonical region. `merge` iterates `other.regions` by region key and writes only into `self.regions.entry((region_x, region_z))` — the same key (common.rs:915, 936, 983-986, 991). No cross-region motion exists anywhere in the merge. So writes dropped in never-kept regions are invisible to canonical regions *through the merge itself*.

**The write-if-AIR machinery, mapped precisely** (all common.rs):
- Dispatcher `merge` :910; region `fully_authoritative` fast path :925-971 (vacant → wholesale chunk move :939-941; occupied → `merge_section_auth_overwrite_nonair` :944-951);
- region `fully_outside` (tile-halo zone) :973-987 → `merge_region_write_if_air` :1095-1125;
- partial-region slow path :989+ with `chunk_fully_auth` :1000-1003, `chunk_fully_outside` :1040-1043, and per-block `merge_section_with_auth_check` :1208-1281;
- `merge_section_write_if_air` :1127-1167 — writes other's non-AIR **only where `self_section.storage.get(idx) == AIR`**;

The direction that matters for canonical output is a neighbor tile's 64-block tile-halo (`TILE_EDITOR_HALO`, tile.rs:51) written **into a kept region** and landed via write-if-AIR — e.g. a tree canopy crossing a tile boundary inside the cell. A region-keyed guard never drops those (the write position is in a kept region), so this danger zone is safe under a keep-rectangle guard.

**Where dropped halo writes ARE observable** — reads:
1. **In-tile reads during placement**: `check_for_block` (mod.rs:1551), `check_for_block_absolute` (:1570), `block_at` (:828), `block_exists_absolute` (:1622), `highest_block_between` (:1629, common.rs:697 — tree-canopy roof probe), `get_block_absolute` (:1634), and the whitelist/blacklist read inside `set_block_with_properties_absolute` (:1457). Any of these reading a never-kept position and branching a write at a kept position is a divergence. Same-position reads (the if-absent semantics, common.rs:795-806; whitelist path) are safe — they only affect the dropped position itself.
2. **In-tile post passes** (run inside tile editors over strict bounds but reading through the tile's world, which includes its halo-region writes): `generate_ground_region` (data_processing.rs:747), `carve_region` caves (:793), `carve_lc_water_region` (:801), `sweep_floating_veg_region` (:818), in-tile tunnel carves (:827-838), `seal_floating_fluid_region` (:845). Neighborhood-dependent (seal/enclosure/veg-below checks) — the crisp point: **stream-to-disk eviction never exposed these**, because tile editors are never evicted; a write-time drop in tile editors exposes all of them for the first time.
3. **Post-merge main-editor passes** (non-eviction parallel path, data_processing.rs ~1049-1140): `apply_deepslate`, `caves::carve`, `carve_lc_water_pass`, `sweep_floating_veg`, rail/highway tunnel carves, `seal_floating_fluid_region`, and `models_3d_pipeline.place` (:~1139) — 3D model placement reads the merged world and can straddle the keep boundary (this is exactly why `model_regions` are kept resident under eviction, data_processing.rs:612-619).
4. **The verification harness itself**: `ARNIS_BLOCK_HASH` deliberately hashes leftover halo regions so `hash_acc` equals the whole-world hash (data_processing.rs:1158-1163; order-independent fold, common.rs:620-626). A write-time drop changes the reported whole-world hash **by construction** even when all canonical regions are byte-identical. Any experiment must compare canonical-region hashes only (`region_content_hash`, mod.rs:605 / common.rs:628).

**Safer variant worth noting**: dropping at **merge time only** (guard in the common.rs:915 loop) leaves tile editors intact — bit-identical to today's shipped eviction behavior for canonical output (halo regions are only ever read post-merge by hash_acc and the non-eviction post passes), frees main-editor halo RAM earlier, but saves little CPU since the halo cost lives in the tile editors.

## (1) Dominant data structures and layouts

**The write target** is a 4-level nested hash structure (`src/world_editor/common.rs`):
- `WorldToModify.regions: FnvHashMap<(i32,i32), RegionToModify>` — common.rs:610-612
- `RegionToModify.chunks: FnvHashMap<(i32,i32), ChunkToModify>` — common.rs:591-593
- `ChunkToModify.sections: FnvHashMap<i8, SectionToModify>` — common.rs:544-547
- `SectionToModify` = `BlockStorage` + `properties: FnvHashMap<usize, Arc<Value>>` — common.rs:283-287

`BlockStorage` (common.rs:152-157) is the good part: `Uniform(Block)` (2 bytes), `Full(Vec<u8>)` (4096 B), `FullWide(Vec<Block>)` (8 KiB), promoted lazily on first differing write (common.rs:174-207). Index order is YZX (`y%16*256 + z*16 + x`, common.rs:334-337), so x-scans are byte-contiguous. Every single-block write is 3 FNV hashes + 3 bucket probes + a pointer chase to a heap 4-KiB array (`set_with_props_if_absent`, common.rs:775-808).

**The read-side grids sampled per block** are rows-of-Vecs, i.e. one heap allocation per row:
- elevation `heights: Vec<Vec<f32>>` — `src/elevation/mod.rs:29`, sampled bilinearly (4 corners across 2 non-adjacent row allocations) in `ground.rs:694-724`, reached from `get_ground_level` on **every ground-relative `set_block`** (world_editor/mod.rs:702-717 → ground.rs:614-622)
- land cover `grid: Vec<Vec<u8>>`, `water_distance: Vec<Vec<u8>>` — `src/land_cover.rs:62-65`, sampled at `ground.rs:509-519`

**Element-side:** flood fills are shared `Arc<Vec<(i32,i32)>>` (floodfill_cache.rs:21, no deep copy for landuse/natural/leisure), footprint masks are 1-bit `CoordinateBitmap`s (floodfill_cache.rs:66-80). Buildings additionally build per-building `std::collections::HashSet/HashMap<(i32,i32)>` (SipHash) — see (2).

Note on scope: the `element_placement` bench span (`place_dur`, data_processing.rs:669-943) covers the whole parallel tile phase — `process_element` **plus** per-tile ground generation, land scatter, deepslate, water carve (data_processing.rs:673-855). Tile merge is reported separately as `tile_merge` (data_processing.rs:944).

- **Uniform→Full promotion**: `vec![base; 4096]` alloc+memset per section on first mixed write (common.rs:180-193); Full→FullWide re-collects 8 KiB (common.rs:196-203). One per touched section — inherent, bounded.
- **`bresenham_line` returns a fresh `Vec` per segment** (bresenham.rs:3-19) and several building styles recompute the *same* segment line once **per level**: buildings.rs:1987 (inside the `for level` loop at 1976), similarly 3601, 3871, 3973, 5449, 5474, 5530. Highways/aeroways allocate one per segment (highways.rs:1297-1298, 2384, 2556, 2621) — per-segment is fine; per-level×segment is churn.
- **Per-building footprint `HashSet` rebuilt repeatedly**: `floor_area.iter().copied().collect()` at buildings.rs:4641, 4961, 5336, 5810, 5964, 6050, 6692, 7140 and landuse.rs:150-152 — the same cells re-hashed (SipHash, tuple keys) up to several times per building.

- `BlockWithProperties.clone()` sites (buildings.rs:3113, 3161, 3224…) are Arc refcount bumps — cheap, already fine. Crop NBT compounds are interned (landuse.rs:620-638). String `format!` churn lives in `to_section` (save phase, common.rs:352-354/438-441), not placement.

## (3) Working-set shape

Placement is **tile-streamed with a triple-touch and a replay multiplier**, not a single pass:

1. Elements are assigned to **every** tile their AABB+halo intersects (tile.rs:178-260: areas by editor halo, linears by `linear_halo`, nodes by halo too). A polygon straddling k tiles is fully re-processed k times; its whole flood-fill Vec is re-streamed and every out-of-bbox cell is rejected one `xzbbox.contains` at a time (world_editor/mod.rs:1441-1444). This tile-level duplication is *inside* the place span and is on top of the cell-level 2.94 cpu-s halo already measured.
2. Within a tile (576-640² haloed), elements are visited in OSM-order — random jumps across the tile, but each element's writes are local. Per-tile ground gen is explicitly chunk-by-chunk (ground_generation.rs:13, 214-227) — the best-behaved writer. Per-tile resident set: ~1024 chunks × a few mixed sections × 4 KiB ≈ 10-30 MB per tile editor, × `tile_batch_size` concurrent tiles.
3. Every placed block is then **read out of the tile world and written into the main world** at merge (common.rs:892-…), and read again at save. So each block is touched ≥3× end-to-end. The merge fast path does move whole chunks by pointer when the dest entry is vacant (common.rs:1036-1040), so only halo-overlapped chunks pay the per-index loops — but under band ordering with 9-contributor regions, halo overlap is the common case for boundary chunks.
4. The scattered-read component: every ground-relative `set_block` bilinear-samples the elevation grid (2 row pointers + 4 f32 across 2 separate allocations, ground.rs:710-713); road/ground code additionally samples `cover_class`/`water_distance` per cell (highways.rs:2560-2566, ground_generation.rs). For a 2304² cell these grids are ~25-30 MB — larger than L2, shared by both rayon threads and (as identical copies) by all 16 processes. This is a plausible seat for uniform bandwidth inflation, but **that attribution cannot be proven from reading code** — see experiment below.

mimalloc is already the global allocator (main.rs:70-73), so the storms above cost bandwidth/page-touches more than allocator lock time.

## (4) Three cheapest output-invariant memory-traffic reductions, ranked

**R1 — Merge-section fast paths** (`src/world_editor/common.rs:1127-1203`, also 1220-1266). (a) Hoist `other_section.properties.is_empty() && self_section.properties.is_empty()` out of the 4096-iteration loops — it removes up to 2 hash ops × 4096 × sections; (b) when the dest is `Uniform(AIR)` with empty properties, replace the storage wholesale (memcpy/move of the 4-KiB Vec) instead of 4096 `get/set` with a memset-promotion first. Output safety is airtight: final block content is identical by construction, `content_hash` is storage-representation-independent (common.rs:614-661), and every serialize path compacts first (`save()` → `compact_sections` mod.rs:1704; flush worker mod.rs:1917-1920), so representation can't leak into bytes. *Honesty*: this lands in the `tile_merge` span, not `element_placement` — but merge is serialized on the critical path per batch and shares the bus with the other 15 processes' placement. Its share is measurable today: `--benchmark` already prints `tile_merge` vs `element_placement`; if `tile_merge` is <5% of a cell, this drops to rank 3.

**R2 — Flatten the sampling grids** to a single contiguous allocation + stride: `heights: Vec<Vec<f32>>` (elevation/mod.rs:29, indexed ground.rs:710-713), `grid`/`water_distance: Vec<Vec<u8>>` (land_cover.rs:62-65, indexed ground.rs:515, 530-ish). Bilinear reads currently chase 2 row-Vec pointers per sample on the hottest read path in placement (every relative `set_block` → mod.rs:704-717 → ground.rs:614-622). Flattening changes zero arithmetic — same f32 values, same f64 lerp — so output is byte-identical by construction. *Honesty*: the row-pointer array itself is small and likely cached; the win is fewer dependent loads and better spatial locality between z0/z1 rows. Magnitude unknowable from code. Experiment: patch, then run the ring-3 single-cell probe **and** the 81-cell contended bench; a gain that *grows* with N (like the GPU result: -28%→-31%) confirms bandwidth relief, a flat gain (like the blur transpose: +2.5% at both N=1 and N=16) means it was pure CPU and not the contention seat.

**R3 — Amortize the per-block descent + ground lookup over vertical runs.** `fill_blocks` (mod.rs:1482-1516) calls `set_block` per (x,y,z); each call redoes `xzbbox.contains` twice (mod.rs:1393 and 1441), the flushed-region probe, the 3-map descent, **and a full bilinear `get_absolute_y` per Y even though it only depends on (x,z)** (mod.rs:1399, 686-690). The same pattern hand-rolled: building walls/shutters loop `for y/h { editor.set_block(...) }` (buildings.rs:1960-1963, 3108-3120), floors per column (buildings.rs:4723-4750), highway posts (highways.rs:993-995). A column-run helper that resolves ground Y once per (x,z) and the chunk once (the template already exists: `fill_column`, common.rs:811-855, and `set_with_props_if_absent`'s single descent) issues the identical writes in identical order → byte-identical. *Honesty*: plausibility medium-high for CPU, medium for *contended* gain — the descent is hash math + hot-cache probes, not obviously DRAM-bound; run the same N=1-vs-N=16 discriminator as R2.

**Runner-up (cheap but smaller):** build the footprint `HashSet` once per building and pass it down instead of re-collecting at buildings.rs:4641/4961/5336/5810/5964/6050/6692/7140; hoist the per-level `bresenham_line` out of the level loops (buildings.rs:1987 et al.). Keep the `std` SipHash `HashSet` type — several of these sets *are* iterated (e.g. buildings.rs:6076 `used`), so swapping the hasher changes iteration order and is exactly the kind of change the golden gate exists to catch; content-identical reuse is safe, hasher swaps are not.

**What I cannot tell without an experiment:** which of (grid sampling reads / hash-descent writes / merge streaming / Uniform→Full memsets) actually carries the 37-46% inflation. Discriminating measurement: run one ring-3 cell alone vs 16 concurrent under a bandwidth profiler (VTune memory-access analysis or AMD-equivalent uProf; on this Windows box VTune's `-collect memory-access` on the arnis process), comparing DRAM-bandwidth-bound % and average load latency between N=1 and N=16; the structure whose latency inflates ~1.4× is the seat. Cheaper proxy without a profiler: apply R1/R2/R3 individually and accept only the ones whose cells/min gain at N=16 exceeds their gain at N=1, per the phase-4 rule that flat gains are not contention fixes. All three keep golden hashes 5/5 + `ARNIS_BLOCK_HASH` valid as the acceptance gate.

## 1. What is decoded per cell, and what the bbox filter throws away

**Decoded:** every element of every covering z11 tile, fully materialized: `OsmElement` with `Option<HashMap<String,String>> tags`, `Option<Vec<u64>> nodes`, `Vec<OsmMember>` (`osm_parser.rs:83-93`), via `serde_json::Deserializer::from_reader(BufReader)` (`osm_parser.rs:149-150`) — the slowest serde_json read path, one HashMap + String allocs per element. Tile loop is serial, x-major then y (`osm_parser.rs:141-143`). MEASURED (phase-2 annex §1, §4): 18.6 MB/s single-threaded; Bucharest cs4 bench = 4 distinct tiles (18.8/33.7/61.7/147.8 MB), 90 decodes across 72 cells, **8.20 GB decoded vs 262 MB distinct = 31.3×**; 56 cells read 1 tile, 15 read 2, 1 reads 4; 441 cpu-s/run = 11.4% of the whole machine, 97% of it re-decode.

**Thrown away:** the filter is applied only *after* full decode and full coordinate transform, in `parse_osm_data`:
- Nodes: **none are thrown away at decode** — every node in the tile is transformed and inserted into `nodes_map` (`osm_parser.rs:914-930`); only tagged nodes inside `xzbbox` become output elements (`osm_parser.rs:934-936`). This node pass is O(tile), not O(cell) — the 31× waste is paid a *second* time inside `parse_osm`.
- Ways: clipped by `clip_way_to_bbox`, dropped if empty (`osm_parser.rs:1004-1011`).
- Relations: dropped if not multipolygon/building or if no member survives (`osm_parser.rs:1040-1155`).

Fraction: MEASURED geometric over-read is **45.9×** (5.32 km² kept per cell vs 195 km²/tile; annex §4). The *element*-survival fraction was never counted — DERIVED from area ratio it is roughly 2–6%, but density is not uniform. **Cannot tell exactly without an experiment**: add two `--debug` counters in `parse_osm_data` (elements in = `data.total_count()`, already printed at `osm_parser.rs:884`; elements out = `processed_elements.len()` before return) and run one ring-3 cell; discriminator: out/in ratio. Crucial trap (annex §2c, verified at `osm_parser.rs:958-961, 1035-1044`): you **cannot** pre-filter nodes to the bbox at decode time — `clip_way_to_bbox` needs out-of-bbox endpoints, and unresolved node refs silently break polygon rings. The safe unit of pre-parsing is the whole tile, unfiltered.

## 2. Artifact options

**Recommended: per-tile binary sidecar of the exact `Vec<OsmElement>` in file order** — `osm_g1_z11_{x}_{y}.osmbin` next to the `.json`, decoded in `from_tile_dir` with fall-through to JSON on any anomaly.

Format choice, against the actual data shape (tags = `HashMap<String,String>` per element):
- **bincode or postcard (serde-derive on the existing structs):** the only options that are *byte-identical by construction* — same `OsmElement` sequence, same order, same in-memory type; zero changes to `parse_osm_data`. Cost profile: they remove the JSON **tokenizer** but keep every HashMap/String **allocation**. Either is fine; postcard's varints make a smaller file, bincode is the more boring dependency. Caveat: neither is self-describing — a struct-shape drift decodes to garbage, hence the codec-version key (§4). One serde nuance to preserve: today's reader never calls `.end()` (`osm_parser.rs:149-150`), so trailing bytes after the JSON are tolerated — the sidecar bake must read the source the same way (annex flaw #1: `from_slice` free function would reject such tiles and silently drop them via the `skip unreadable tile` arm at `osm_parser.rs:151-156`).
- **flatbuffers / rkyv (zero-copy):** the only way to *also* kill the allocation cost — but then the decoded thing is no longer `OsmData`, and `parse_osm_data`, `filter_tags` (`osm_parser.rs:66-71`), `SplitOsmData` all consume owned `HashMap`s. Converting archived→owned pays the allocations back; refactoring the consumers touches the order-load-bearing chain (§3). Phase-2's own review scored the mmap/zero-copy variant (D2-T7) 35% and shelved it. Do not start here.
- **mmap vs read:** MEASURED ≈ 0 (annex §1: 262 MB is fully page-cached on a 31.4 GB machine; the cost is deserialization, not `read()`). mmap only earns its keep with a zero-copy format, i.e. not in phase A.

**Who writes it:** a one-shot arnis mode (`--osm-bake-tile <json> <out>` or bake-on-first-miss inside `from_tile_dir` with tmp + atomic rename, first-writer-wins) — the encoder and decoder must be the same Rust structs, so Meld/Python cannot write it. Meld's role is only orchestration: bake after `_download_one` publishes (`prefetch.py:222-226`) and after `merge_tiles`. Known gotcha if it's a CLI mode: new early-exit modes need the `validate_args` exemption + a `gui.rs` Args field (documented in memory + annex flaw on D2-T4).

**Not recommended:** a merged per-cell artifact (freezes the cross-tile dedup at bake time and has near-zero reuse — the per-tile unit is the whole point), and re-tiling to z13/z14 (annex §5c: **not byte-identical** — `from_tile_dir` does no clipping, the tile set *is* the element universe; shrinking tiles drops distant member ways of large multipolygons and changes ring assembly at `osm_parser.rs:1071-1078`).

## 3. Where dedup happens today, and what must be preserved exactly

- **The only cross-tile dedup at generation time** is `osm_parser.rs:157-162`: `seen.insert((el.type.clone(), el.id))`, **first-occurrence-wins**, over tiles visited **x ascending, then y ascending** (`osm_parser.rs:141-143`), each tile contributing its JSON array order. (The Python `merge_tiles` dedup at `osm_grid.py:94-111` is bake-time only, same (type,id) first-wins.)
- Why order is world bytes (annex §2c, each link verified): `SplitOsmData` buckets preserve order (`osm_parser.rs:203-224`) → `processed_elements` push order is nodes, ways, relations in bucket order (`osm_parser.rs:936, 1030, 1150`) → `main.rs:560` `sort_by_key(get_priority)` is a **stable** sort, so ties (most of the vector; `get_priority` returns 0-6, `osm_parser.rs:1582-1596`) keep parse order verbatim → `process_element` writes overwrite earlier writes at the same block.
- Therefore the sidecar must: (a) store each tile's element sequence **verbatim in file order** (no sorting, no per-tile dedup, no tag filtering — `filter_tags` runs later and its list can change without invalidating artifacts); (b) leave the merge loop untouched — per-tile artifacts slot under the existing `for x { for y {` and the existing first-wins `HashSet`, so merge semantics are preserved *by not reimplementing them*; (c) reconstruct `type` as the exact original string — `SplitOsmData` matches on it and unknown strings must still land in `others` (`osm_parser.rs:207-212`); a u8 discriminant on disk is fine only with a lossless "other" escape; (d) roundtrip serde edge cases losslessly: `tags: None` vs `Some(empty)`, `nodes: None` vs `Some(empty)`, `members` default-empty (`osm_parser.rs:83-93`), non-ASCII tag values, float lat/lon bit-exact (they feed `LLPoint`→`transform_point`→integer block coords; store f64 bits, never text).
- One extra hazard the artifact must not disturb (annex): the `PartGroups` insert order between `compute_outline_suppression` and `compute_spatial_part_suppression` (`osm_parser.rs:891-897`) is load-bearing — untouched as long as the artifact reproduces the element vector exactly.

## 4. Versioning / keying so a stale artifact can never be used

Key = all three of:
1. **Source-content hash**: xxh3/sha256 of the exact `.json` bytes + byte length, stored in the sidecar header, re-hashed on every read (DERIVED: hashing 262 MB of page-cached bytes ≈ 0.1 s/run, ~2 orders cheaper than the 441 s it replaces). Content hash — not mtime — because the same filename is legitimately rewritten by TTL re-downloads (`prefetch.py:314-326`, 365 d), by re-fetch after `_fresh_on_disk` fails, and by the `.pbf` bake, and because downloaded vs baked tiles of the same (x,y) have different bytes/order.
2. **Codec version**: a dedicated `OSM_SIDECAR_CODEC_VERSION` const bumped whenever `OsmElement`'s serde shape or the encoding changes — deliberately *not* `CARGO_PKG_VERSION`, or every arnis release forces a global re-bake for nothing. (Meld's `g1` in the filename, `osm_grid.py:51`, already versions the *query shape* and rides along in the sidecar's name.)
3. **Fail-open read path**: any header mismatch, short file, or decode error → silently fall through to the `.json` (and optionally re-bake). Never error, never trust the sidecar's own header over the hash.

Non-negotiable caveat from the phase-2 verification pass (annex, D2 review): the content hash protects against **staleness only, never against a wrong encoding of correct input** — a codec bug produces silently different worlds on every site until someone deletes the sidecars, and **no existing gate can see it**: `golden_hash.sh` feeds `--file --offline` so `from_tile_dir` never executes, and `ARNIS_BLOCK_HASH` hashes placed blocks, which would be wrong in *both* arms. Required gate: a `MELD_OSM_CACHE_VERIFY` mode that decodes both the sidecar and the JSON and compares the element sequences, default-ON for the first N runs (or first sighting of each tile), plus `ARNIS_BLOCK_HASH` parity with-and-without the sidecar over every cached tile.

## 5. Honest per-cell saving

What the two markers actually contain:
- `osm_fetch` 946 ms (ring-3 cell, T=2) = `File::open` + serde_json `from_reader` decode + first-wins dedup of that cell's covering tiles. A sidecar attacks **only the decode**, and only its tokenizer half unless zero-copy: file read is a page-cache memcpy (≈0), the dedup HashSet stays, and bincode/postcard still performs every HashMap/String allocation JSON did.
- `parse_osm` 646 ms = `parse_osm_data`, which the sidecar leaves **completely untouched** (identical `OsmData` in). **Saving here: 0 ms.** The O(tile) node/way passes inside it are a separate lever (finer tiles / pre-filtering), and both are output-changing.

So the sidecar's per-cell ceiling is strictly < 946 ms, and the honest number depends on the tokenize-vs-allocate split, which **is not measurable from the existing data** — the only rate measured is 18.6 MB/s end-to-end from one tile (annex, flagged single-sample). DERIVED brackets: if tokenizing is ~2/3 of decode (typical serde_json-vs-bincode gap), 946 → ~350-450 ms, i.e. ~3-4% of the profiled cell; if allocation dominates, 946 → ~650-750 ms, ~1-2%. Run-wide the picture is better than the ring-3 cell suggests, because the centre tile (147.8 MB) is decoded 42× and ring-3 cells sample the cheap quadrant: MEASURED 441 cpu-s of decode per run; a 3× faster decode saves ~294 cpu-s ≈ 7.6% of machine capacity (DERIVED) — against the 50-cells/min target that is on the order of a third of the required 20% contended-CPU cut, plus an unquantified second-order relief because JSON decode is exactly the allocation/bandwidth-heavy work the uniform 1.46×@N20 inflation points at. Do not book that second-order effect without measuring it.

**Discriminating experiments (in dependency order):**
- **E1 (prices everything, ~half a day):** the annex's D2-T2 — swap `from_reader` → `Deserializer::from_slice` (the deserializer form, *not* the `end()`-calling free function) + `(u8,u64)` dedup key at `osm_parser.rs:149-162`; run one ring-3 cell twice: `arnis.exe --bbox <cell bbox> --osm-tile-dir C:\tmp\meld-ab-data\cache\osm --osm-tile-z 11 --benchmark <bench flags>` and compare the `osm_fetch` mark. Discriminator: ≥1.5× faster → tokenizer dominates → sidecar is worth building (5-20× on decode plausible); <1.3× → allocation dominates → bincode/postcard caps near 2× and only a zero-copy refactor (high risk, §2) captures more. This was the annex's own gate for D2-T3 and it is still unrun.
- **E2 (bbox survival):** the two debug counters from §1; expected ~2-6% survival, confirming the waste lives in decode+node-pass, not in clipping.
- **E3 (sidecar decode cost):** bake the 147.8 MB tile (`osm_g1_z11_1172_741.json`, 1.19 M elements) to bincode in a scratch binary, time `decode → Vec<OsmElement>` vs the 7.9 s JSON figure; the ratio is the honest sidecar multiplier.

**Bottom line:** per-tile bincode/postcard sidecar of the verbatim element sequence, keyed on (source-bytes hash, codec version, g1/z in the name), fail-open to JSON, verify-mode default-ON, dedup/merge left exactly where it is at `osm_parser.rs:157-162`. Ceiling without a consumer refactor: removes most of `osm_fetch` (upper bound ~946 ms/cell profiled, ~441 cpu-s/run measured run-wide), removes none of `parse_osm`. Run E1 before writing the sidecar; it can halve or kill the business case in one afternoon.

## A) HYBRID CORES (8P+16E): is P-core pinning worth anything?

**What the code actually does (evidence):**

Plus the flush pool: `(cores/4).clamp(2,6)` = 6 more threads under eviction (`arnis-triagefix/src/world_editor/mod.rs:1878-1888`, spawn at 1908).
- Nothing anywhere sets affinity, priority, or QoS. Grep of `arnis-triagefix/src/**/*.rs` for affinity/SetThread/SetProcess/priority: zero hits outside comments/JS libs. So Windows' Thread Director makes all placement decisions today, for up to 12-20 workers x 21 rayon threads = 252-420 runnable threads (derived) on 24 logical CPUs.
- The red-herring record is in the Meld repo, not arnis: `C:\Users\LEGION\Documents\Meld\docs\perf-adaptive-scheduler-research.md:106` ("DO NOT pursue: process-priority/EcoQoS tweaks (previously proven red herrings)"), same file :158 ("Consider pinning P-cores for the serial phases via worker count rather than priority tweaks (EcoQoS proven red herring)"), :220, :563 (pruned from the benchmark matrix), and `docs\perf-adaptive-scheduler-plan.md:28`.

**Honest assessment:** P-core pinning for the first N workers most likely does NOT move fleet throughput, for two reasons grounded in your own measurements. (1) The contention signature is uniform 2.04-2.07x inflation across place/save/elev — a package-shared resource (DRAM bandwidth / shared cache). Pinning re-labels which worker owns the fast cores; it adds zero bandwidth, and at the measured 93%-of-ceiling efficiency the scheduler is not the residual. (2) At the N=16 throughput peak the box runs 76-79% CPU — threads are not queueing for P-cores; if placement were the binding constraint you would expect CPU pegged and non-uniform phase inflation. The one channel where hybrid asymmetry could still matter is the SERIAL sections (parse_osm, Overture decode, batch merge — all single-threaded per research.md:109): a serial phase that Thread Director parks on an E-core runs at E-core IPC and stretches that cell's critical path. That affects per-cell latency/tail, not necessarily throughput, and with 250+ runnable threads the director's P-core preference is already mostly defeated by saturation. Note the priority/EcoQoS red-herring result is adjacent evidence but not the same experiment — priority classes never overrode Thread Director's P/E placement; hard affinity would. So: probably irrelevant, but not proven.

**Cheap discriminating experiment (no code change):** run the existing single-cell T=2 profile (uncontended 23.3-24.5 cpu-s baseline) twice with hard affinity, e.g. `Start-Process arnis.exe -ArgumentList ... ; $p.ProcessorAffinity = 0xFF` (P-cores, logical 0-7 on 8P-noHT+16E) vs `0xFFFF00` (E-cores) — or `cmd /c start /affinity FF`. Set `RAYON_NUM_THREADS=8` for the P run and `=16` for the E run isn't needed for the discriminator; keep T=2 as in the existing profile so it is apples-to-apples. Compare **cpu-seconds, not wall**. Expected outcomes: if E-pinned cpu-s is within ~10% of P-pinned, per-instruction throughput is memory-bound even uncontended and core placement is confirmed irrelevant — close the topic. If E-pinned costs 1.3x+ cpu-s, hybrid placement is real, and the follow-up is one fleet A/B: the 81-cell benchmark at N=16, default vs 8 workers affinitized 0xFF + 8 to 0xFFFF00 (settable via the already-present Job Object `Affinity` field in childproc.py, or `$p.ProcessorAffinity` post-spawn), 2 repeats each; a win must exceed the existing 138.4-144.8s run-to-run spread (±2.3%, derived) to count.

## B) ALLOCATOR + NBT: per-region/per-chunk churn in the save path

Setup: mimalloc is global (`arnis-triagefix/src/main.rs:70-73`, Cargo.toml:42). Save fans out per-region via `par_iter` (`src/world_editor/java.rs:205-215`, `save_single_region` at 271) into the free-standing `write_region_to_disk` (java.rs:414), which is shared with the FlushWorker streaming path (comment java.rs:403-404). Per kept region it serializes up to 1024 chunks. The per-REGION buffer discipline is already decent: one `ser_buffer` per region, `clear()`ed and reused across chunks (java.rs:429, 477-478) — no fix needed there. The churn is per-CHUNK, x1024 per region, x16 kept regions per cs4 cell (derived from the 36-generated/20-skipped ground truth). Ranked by memory traffic:

1. **Anvil sink: fresh zlib encoder state + zero-capacity output Vec per chunk (dependency, not this repo).** `fastanvil-0.32.0/src/region.rs:322-327` (`~/.cargo/registry`): `write_chunk` does `let mut buf = vec![];` then `ZlibEncoder::new(..., Compression::fast())` and `read_to_end`. flate2 1.1.9 uses the miniz_oxide backend (Cargo.lock:1664-1670), whose compressor state is a boxed struct of order hundreds of KB (dictionary + hash tables; magnitude derived, not measured) that is allocated and initialized per chunk, plus doubling-growth reallocs of `buf` from capacity 0. That is real per-chunk memory traffic ~1024x per region. Fix: bypass `write_chunk` and call `write_compressed_chunk` (region.rs:334) with a thread-local reused `flate2::Compress` (reset between chunks) and a reused output Vec. Same miniz_oxide version + same `Compression::fast()` level produces an identical deflate stream, so .mca stays byte-identical — verify with golden hashes as ritual. Caveat: the benchmark path is blinear, so this helps Anvil-output runs only.

2. **Blinear sink (the benchmark path): three copies of every chunk's NBT + fresh zstd context per bucket.** Copy 1: `ser_buffer` (java.rs:478). Copy 2: `BlinearRegionWriter::write_chunk` does `nbt.to_vec()` into `slots` (`src/world_editor/blinear.rs:92-93`) — unavoidable given ser_buffer reuse. Copy 3: `encode_bucket` re-copies all 64 slots into a fresh `raw` Vec (`blinear.rs:222-234`) before `zstd::bulk::compress(&raw, level)` (`blinear.rs:239`), which creates and tears down a one-shot zstd CCtx per bucket — 16 buckets/region, and a level-6 CCtx workspace is MB-scale (derived from zstd internals, not measured). Fixes that cut traffic without changing bytes: reuse a thread-local `zstd::bulk::Compressor` across buckets (identical output for identical params/version), and/or frame chunks directly into per-bucket buffers at `write_chunk` time to delete copy 3. The `raw`/`out` capacity hints (blinear.rs:222 `1<<19`, :169 `1<<20`) likely undershoot real 1:1 region sizes, adding growth reallocs — cannot tell the realloc count without measuring actual bucket sizes.

3. **Per-chunk NBT tree of `HashMap<String, Value>` with 24-25 `biome_value.clone()`s.** `create_chunk_nbt` (java.rs:1073) builds one `HashMap<String,Value>` per section across the full -4..=19 range (java.rs:1106-1144) with `String` keys allocated per insert, and clones the chunk's biome compound into EVERY section: `section_nbt.insert("biomes".to_string(), biome_value.clone())` at java.rs:1118 — ~24 Value-tree clones per chunk, ~400k per region (derived). Plus per-chunk `post_processing` Vec (java.rs:1152) and empty-list values (java.rs:1171-1173). mimalloc makes the allocs cheap in time, but the copies are traffic. Fix shape: a `#[derive(Serialize)]` chunk struct holding `&Value` borrows for biomes (fastnbt serializes borrowed data), eliminating the clones and most String-key allocs. Larger refactor; byte-identity must be proven since NBT key ORDER can change when leaving HashMap (HashMap iteration order is already non-deterministic, so fastnbt must be sorting or the format tolerates it — check before claiming byte-identity; the block_hash gate is the safety net).

4. **Minor, hot-path but small:** `chunk_to_modify.other.clone()` per content chunk regardless of whether the dedup applies (java.rs:447-452) — free when `other` is empty, real when block entities exist; could clone only when a `block_entities`/`entities` list is present. `sections().collect()` (java.rs:454 via common.rs:585-587 `to_section`) materializes palette+data Vecs per section — that is the required output data, not churn to reclaim.

5. **NOT hot in this benchmark:** pass-2 base-chunk fill allocates a fresh 8KB Vec + `to_vec()` of cached sections per empty chunk (java.rs:113, 99) but is skipped whenever the region already has all 1024 chunks (java.rs:485-487), the common case after ground gen at 1:1.

**Cannot-tell-without-experiment:** whether any of this moves the 18% save number, since save inflates uniformly with the other phases (bandwidth-shaped). Discriminator: single-cell T=2 profile with fix 2 (zstd Compressor reuse + copy-3 removal, ~30 lines) vs baseline, comparing save-phase cpu-ms AND the run at N=16 — if save cpu drops but N=16 throughput drops nothing, the reclaimed traffic was not the shared-resource bottleneck; if N=16 gains more than the N=1 saving (as GPU caves did, -31% at 8 concurrent), it is relieving the real contention. Gate: `ARNIS_BLOCK_HASH` + golden 5/5, never byte-comparing .b_linear.
