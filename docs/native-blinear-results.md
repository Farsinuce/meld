# Native B_Linear generation — implementation and measured results

**Branch:** `meld-blinear` in both repos (arnis fork and light-meld). Local commits only.
**Date:** 2026-08-20
**Status:** implemented, tested, benchmarked. Ships default-off as experimental.

Companion to [native-blinear-generation.md](native-blinear-generation.md), which is the
plan this executed against. This document is what actually happened and what it measured.

---

## Version requirement (read this first)

**A world generated with `--region-format blinear` can only be opened by Leaf 1.21.11
(June 2026 builds) or newer, or any Leaf 26.x.** Nothing else reads it:

- Paper, Purpur, Spigot, Folia upstream: **no**
- Leaf 1.21.8 and older: **no** (the format was not in those builds)
- The vanilla Minecraft client / single-player: **no**
- Leaf 1.21.11+ / 26.x with `misc.region-format.format-name: B_LINEAR`: **yes**

The server config that makes it work is written by Meld's server setup automatically.
There is no `.mca` original kept alongside, so the fallback is to run
`region_converter --to mca` on the world.

Verified directly rather than taken from documentation: Leaf's `EnumRegionFormat` maps
`B_LINEAR` to the `.b_linear` extension, and a Leaf 26.1.2 install in this repo wrote
`r.X.Z.b_linear` files of its own. The extension is `.b_linear`, not `.blinear`.

## What was built

**arnis fork** (`meld-blinear`, 4 commits)

| Commit | What |
|---|---|
| `1bb821c8` | `--region-format {mca,blinear}` + `--blinear-level 1..22`, the B_Linear v3 writer, container plumbed through both save paths |
| `d8951435` | In-process container-equivalence test |
| `6120d082` | Parallel bucket compression after a measured memory regression (below) |

The container is a field on the existing Java path, not a fourth `WorldFormat`, so
parallel tiles, stream-to-disk eviction, the golden-hash gate and every block-entity
schema stay exactly as they were. The swap point is where the Anvil writer hands its
serialized chunk to fastanvil — one `RegionSink` enum with two variants.

Deliberate exclusions: the GUI stays on Anvil (it writes into `.minecraft/saves`, where
the client has to open the world), and the map item is skipped for b_linear worlds
because its renderer reads regions back through fastanvil.

**Meld** (`meld-blinear`, 3 commits on top of the plan doc)

| Commit | What |
|---|---|
| `4459a43` | `native_region_format` project setting, flag passed to arnis, merge/finalcheck/server-setup taught the second container |
| `a83ad8e` | UI picker with the version requirement stated, settings validation |

Meld never reads region bytes, so the integration is about recognising a second file
name. The one genuinely new rule: merging a cell of one container into a master of the
other is refused up front. Because the file names differ it would not surface as a
collision — it would just leave half a world unreadable.

### T4 in detail — the one that matters

Leaf 1.21.11 build 175 (sha256-verified), `format-name: B_LINEAR`, world generated by
`arnis --region-format blinear`:

- Booted: `Done (12.273s)`, clean shutdown
- **Zero** occurrences of `XXHash32 check failed`, `corrupt`, or any exception in the log
- Force-loaded 256 chunks, then `Saved 1264 block chunks`
- The world stayed 100% b_linear — **0 `.mca` files** — and Leaf wrote 3 new regions of
  its own in the same container
- After Leaf resaved it, all 12 regions still verify: 10,880 chunks ok, 0 discarded
- The resaved regions still contain arnis's city: 1432 `gray_concrete`, 1030
  `smooth_stone`, 1008 `polished_blackstone`, 681 `white_concrete`, 206 `glass_pane`

So the full round trip holds: arnis writes → Leaf reads → Leaf writes → our tools read.

### Block-level verification — are blocks actually in the right place?

The container tests prove the same NBT comes back out. These decode it and compare the
resolved block at every position, so a wrong bucket index or a swapped chunk would show
as blocks in the wrong place rather than as bytes that merely differ. Each world is also
checked against itself: the chunk in slot *i* must carry `xPos`/`zPos` that map back to
slot *i*.

| World (same seed, one run per container) | Chunks | Chunks misplaced | Non-air positions compared | Positions differing |
|---|---|---|---|---|
| Farmland, flat (seed 42) | 6,144 ×2 | **0** | 4,958,282 | **0** |
| Dense city, buildings (seed 99) | 16,384 ×2 | **0** | 22,326,618 | **0** |
| Terrain + caves + baked lighting (seed 11) | 4,096 ×2 | **0** | 11,891,414 | 69 |

**27.3 million block positions across 22,528 chunks with zero differences** on the first
two. The third needs its own explanation, and it is not the container:

| Control: two runs, **both Anvil**, same seed, caves on | Positions compared | Chunks differing | Positions differing |
|---|---|---|---|
| `.mca` run A vs `.mca` run B | 12,147,012 | 15 | **158** |

Two Anvil runs of the same seed disagree *more* than Anvil-vs-B_Linear did (158 vs 69),
so `--caves` makes generation itself non-reproducible run to run — a pre-existing
property of the fork, unrelated to the container. The differences are alternate materials
on cave props deep underground (oak_planks vs gray_concrete, sand vs grass_block), about
0.001% of positions, not corruption.

**Conclusion:** the container is lossless — proven byte-for-byte in-process, and
block-for-block over 27.3M positions on the content that is deterministic. With caves
enabled, no two runs match exactly whichever container you write, and that was already
true before this work.

### A note on how equivalence had to be proven

Comparing two generated worlds byte-for-byte does not work, and this is worth recording
because it looks like a writer bug when you first hit it. Two `.mca` runs of the same
bbox and seed differ in **8192 of 8192 chunks**: chunk lengths match exactly but the
bytes do not, because palette ordering follows std `HashMap` iteration order, which is
randomised per process.

What is stable is the content itself. `ARNIS_BLOCK_HASH=1` prints an in-memory content
hash, and across **every** combination of container and eviction mode the same bbox and
seed produced the identical hash `0b52cddca680c865`:

| streaming | container | block_hash |
|---|---|---|
| off | mca | `0b52cddca680c865` |
| off | blinear | `0b52cddca680c865` |
| on | mca | `0b52cddca680c865` |
| on | blinear | `0b52cddca680c865` |

Combined with T3 (same bytes in, same bytes out of both containers) and T2 (an
independent decoder validating every chunk), that is the equivalence evidence.

## Side-by-side measurements

Same machine, same bbox, runs interleaved so drift hits both arms equally. Wall-clock
includes a network OSM fetch that varies by 5-15 s between runs, so `save_ms` is the
figure that isolates the container. All numbers are post-fix (commit `6120d082`).

### Dense city — Bucharest, 25 regions, 25,600 chunks

| | Anvil `.mca` | B_Linear `.b_linear` | Delta |
|---|---|---|---|
| Save, best of 3 | 285 ms | **253 ms** | −11% |
| Save, median | 289 ms | **269 ms** | −7% |
| Peak RAM | 761 MB | 1009 MB | +33% |
| **Disk** | 113.36 MB | **30.57 MB** | **3.71× smaller** |
| Conversion pass afterwards | 234 ms | **none** | eliminated |
| Peak disk for the whole flow | 143.93 MB | **30.57 MB** | **4.7× less** |

### Open countryside — Flevoland, 56 regions, 57,344 chunks

| | Anvil `.mca` | B_Linear `.b_linear` | Delta |
|---|---|---|---|
| Save, best of 3 | 256 ms | 271 ms | +6% |
| Save, median | 256 ms | 276 ms | +8% |
| Peak RAM | 524 MB | 673 MB | +28% |
| **Disk** | 224.48 MB | **15.61 MB** | **14.4× smaller** |
| Conversion pass afterwards | 277 ms | **none** | eliminated |
| Peak disk for the whole flow | 240.10 MB | **15.61 MB** | **15.4× less** |

The 14× is real but flattering: sparse farmland is mostly identical base chunks, and
Anvil pads every one of the 1024 chunks to a 4 KiB sector whether it holds anything or
not. **Quote the city number, 3.7×, as the representative figure.**

### At scale — Bucharest, 224 regions, streaming eviction forced on both arms

This is the path Meld uses for large worlds.

| | Anvil `.mca` | B_Linear `.b_linear` | Delta |
|---|---|---|---|
| Wall clock (2 runs) | 73.9 s / 72.1 s | **61.5 s / 66.9 s** | −11% to −17% |
| Final flush | 24 ms / 0 ms | 1 ms / 27 ms | same |
| Peak RAM | 1701 MB / 1691 MB | 1810 MB / 1820 MB | **+7%** |
| **Disk** | 990.2 MB | **245.7 MB** | **4.03× smaller** |
| Conversion pass afterwards | 1473 ms | **none** | eliminated |

### So what does it actually save?

**Disk: 3.7–4.0× on real city data**, and because the conversion flow needs the Anvil
world and the B_Linear world on disk at the same time, **peak disk for the whole flow
drops ~4.7×**.

**Time: the conversion pass disappears** — measured at 234 ms / 25 regions, 277 ms / 56,
1473 ms / 224, i.e. **6.6–9.4 ms per region**. Extrapolating to the 9,408-region
Bucharest build in Meld's own calibration, that is roughly **1.0–1.5 minutes of pure
conversion removed** from a ~30-minute run, plus the double disk write. The write itself
is a wash: at 25 regions B_Linear saves 11% faster, at 56 it is 6% slower, at 224 the
final flush is unmeasurable for both. At scale the wall clock came out 11–17% lower for
B_Linear across both runs, consistent with writing 246 MB instead of 990 MB, though OSM
fetch noise is inside that figure so it is suggestive rather than conclusive.

**Do not promise the 4.3× planning constant or the 14× rural figure.** The honest
headline is: **~3.7–4× smaller on disk for real cities, conversion step gone, memory
+7% at scale.**

## Sizing a real project

Measured on the settings of the Romania project in this workspace — scale 0.05 (1:20),
terrain, caves and baked lighting on, buildings off — over a 4-region sample near Brasov:

| | Anvil | B_Linear | Ratio |
|---|---|---|---|
| Per region | 4.69 MiB | 1.20 MiB | **3.91×** |

Cave-and-terrain content compresses less than the 14× of flat farmland (fuller chunks
waste less of Anvil's 4 KiB sector padding) and lands near the dense-city figure.

| Build | Regions | Anvil | B_Linear | Saved |
|---|---|---|---|---|
| The existing 1:20 Romania project | 3,276 | ~15 GB measured (Meld's own estimator says 37.6 GB) | ~3.8 GB (est. ~9.6 GB) | **~11–28 GB** |
| Romania at **1:1** (20× linear = 400× the regions) | ~1,310,400 | **~6–15 TB** | **~1.5–3.9 TB** | **~4.4–11 TB** |

The wide range is Meld's deliberately conservative planning constant (11.5 MB/region)
against what the generator actually wrote (4.69 MiB/region). Either way a 1:1 Romania is
far beyond the 232 GB free on this machine in *both* containers — B_Linear changes the
multiple, not the feasibility. Where it does pay off today is the 1:20 project: roughly
a quarter of the disk, and no moment where both worlds exist at once.

## The one regression found, and its fix

The first 224-region measurement showed B_Linear peaking at **4.3 GB against Anvil's
1.7 GB** with a 2754 ms final flush. Cause: region writes run on the single background
flush thread during stream-to-disk eviction, and compressing 16 buckets one after
another at zstd 6 was slow enough to stall the eviction queue, so the generator held
regions in RAM waiting for it.

Fix (`6120d082`): buckets are independent, so they now compress in parallel, and each
bucket's raw chunk NBT is released as soon as its frame exists instead of being held for
the whole region. Re-measured with eviction forced on for both arms: **1810 MB against
1701 MB, +7%**, and the final flush is no longer measurable.

The remaining +28–33% peak in the small non-streaming runs is inherent: that path saves
regions in parallel across rayon threads, and B_Linear holds a region's raw NBT until
its buckets are framed, where Anvil compresses and writes chunk by chunk. It does not
apply to large worlds, which stream.

## Open threads

- The GUI has no B_Linear toggle by design; only Meld exposes it.
- `--map-item-only` on a b_linear world fails cleanly with "world has no saved regions".
  A clearer message would be nicer.
- Root `meld/` package tools (`mca.py`, `chunk_protection.py`, `subworld.py`) still glob
  `*.mca` only and would silently no-op on a b_linear world. They are outside the
  light-meld run path; `metadata.json` now carries `regionContainer` as their detection
  hook when someone gets to them.
- Worth deciding before this graduates from experimental: offer a one-click "keep an
  `.mca` archive too" that runs the converter in reverse, for users who want the
  fallback without giving up the disk win.
