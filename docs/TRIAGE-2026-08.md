## Why this exists

Eight defects were reported in `#meld` over 22–23 August. Each was root-caused twice: once by
reading the code, then again by measuring, because the first pass produced confident numbers that
did not survive contact with the data. What was measured:

- **19,018 cell logs** across 37 projects
- **2,428 region files**, parsed chunk-by-chunk through the Anvil container
- **live runs** of both bundled `arnis` binaries against Overture
- matched real builds already on disk in `light-meld/tools/height_test/_work/`

Three first-pass conclusions were overturned by that measurement, and are recorded below so
nobody re-derives them.

## What is in the Meld branch

### 1. `f4a32e7` — RAM readout, and two estimates that disagreed

Reported: a 2×32 GB kit read as “68.3 GB” total and “2×34 GB” per stick, on two machines.

`_sys_stats` and the DIMM probe divided byte counts by `1e9` and labelled the result GB, while
`_total_ram_gb` and `_machine_specs` in the same file used `1024**3`. Windows labels GiB as “GB”
everywhere the user can check us against. Every memory figure now goes through one `_gib()`
helper; disk stays decimal on purpose and both stats say which convention they use in a tooltip.

Two more truth bugs found in the same area:

- `est_mb` called `_mb_per_region()` with no arguments, so `elevation` defaulted to `None` and the
  height term short-circuited to vanilla — while the BUILD panel called it *with* elevation. The
  same project could be quoted 22.4 GB and 2.2 GB in the same second, from the same function.
- `fmtDur` was declared twice at top level in one script block. The later export-progress version
  silently won, so every build estimate rendered in the fine-grained export style — “13m 54s” for
  a number that is a guess. Renamed to `fmtEta`, not deleted; both bodies were wanted.

**Test:** open the app, read the SYSTEM panel. A 64 GiB machine should show ~63.6, not 68.3. The
benchmark report should say `2×32 GB`.

### 2. `8640912` — buildings, and Overture failures becoming visible

Reported as “additional buildings dont seem to work in meld”, with a Meld render showing roads,
water and terrain but no houses, against a standalone Arnis render of the same area full of them.

**Measurement rules Overture out as the cause.** `dist/Meld/data/projects/meld-world-2/Brasov` is
scale 1.0, buildings ON, and Overture failed 100% of the time (all 16 cell logs carry the STAC
404). Parsed block-by-block across 4,096 chunks of its centre regions: **595.3 building blocks per
chunk, doors throughout.** A full city with Overture stone dead. Overture contributes ~18.9% of
buildings in a well-mapped city — worth having, incapable of emptying a render.

What does empty a render:

- `project.py:46` starts every new project with `"buildings": False`. Across every `arnis`
  invocation logged locally, **14,165 of 19,018 (74.5%) carried `--no-buildings`.** Standalone
  Arnis defaults the opposite way. That flag also disables Overture, which is why the Additional
  buildings checkbox greys out and does nothing — the literal complaint.
- `project.py:22` starts every project at scale 1:10, where a 12×8 m house is about one block.
  Same city, buildings on both times: **425.9 building blocks/chunk at 1:1 against 9.6 at 1:10**,
  doors in 46.6% of chunks against 0.26%.

Neither default is changed — both are deliberate and flipping them would slow every first build.
Generate now warns once, at the moment of commitment, in the same warn-don’t-block shape the
existing workers-above-RAM check uses.

Overture failures are also counted per run and surfaced twice: a log line at the end of the run,
and `overture_failed_cells` in the report summary. A cell that loses Overture still finishes —
losing ~19% of a city’s buildings beats losing the cell — but previously the only evidence was a
line on `arnis` stdout.

**Test:** with buildings off, click Generate; a modal should name the consequence. Set scale to
0.1 with buildings on; a second warning should appear. Both must be dismissible and must not
block a scripted `/api/queue` call.

**Still open:** which of the two the original reporter hit. One fresh cell log settles it — grep
for `--no-buildings` and for `Added N buildings from Overture`.

### 3. `0b7a25b` — the selection box could not be cleared

Asked as “how do i remove the yellow border”. The honest answer was that you could not: the draw
control is built with `edit:false` so there is no stock trash, the 🗑️ in the Plan card clears
planned *cells* and never touches the box, and the only code that did clear it lives inside
`#btnNewWorld`, which is `style="display:none"` and whose handler reloads the page before reaching
that block. The box outlived the project it belonged to, and re-drawing far away silently tiled
onto the old lattice.

`clearSelection()` forgets it in all three places that remember one: the Leaflet layer,
`localStorage`, and `project.json` on the server — which already accepted `{selection: null}` and
simply was never sent one. Planned and merged cells are left alone on purpose.

Reachable via a labelled button, `Esc`, and `Delete`. `Esc` unwinds one level at a time
(edit-cells → select-to-retry → the box) so it cannot destroy a mode the user could not see was
armed; both keys stand down inside text fields and while a modal is up.

Also adds a **Show cells on the map** toggle. With hundreds of cells drawn the ground underneath
is genuinely hard to see, which is half of why moving a selection felt impossible.

**Test:** draw a box, press Esc — it goes, and stays gone across a refresh. Draw one, turn on
Edit cells, press Esc — Edit cells turns off and the box survives. Press Esc with a modal open —
the modal closes and the box survives.

### 4. `e7b2f6b` — Quit looking hung, which is what orphaned the workers

Reported as “quitting meld doesnt kill the process it stays”, with two `Meld.exe` at ~17.7 GB
each afterwards.

**Reproducing it changed the story.** A normal exit orphans nothing — pool workers exit 0 and the
job object works. Orphans require a hard kill. The real chain:

> bake running → Quit → tray icon and window vanish at once, while the interpreter blocks in
> `ProcessPoolExecutor`’s exit handler for the whole remaining bake (**346 s** for one Romania
> `.pbf` in the log) → looks hung → user ends the task → *now* the workers are orphaned, because
> a hard kill runs none of our cleanup.

So the visible freeze is the bug. Quit now runs synchronously from the tray with the icon still
up and retitled, instead of being fired on a daemon thread while the icon is torn down. That also
de-duplicates shutdown — `meld_app` called it again once `run()` returned, which is why the log
printed `[meld] shutting down…` twice.

Three real holes closed underneath:

- The `.pbf` bake pool is spawned by `multiprocessing`, which on Windows calls `CreateProcess`
  directly rather than going through `subprocess.Popen` — so `childproc`’s process-wide policy
  never saw the largest memory consumers in the app. **Verified here:** worker `in_our_job` was
  `False` before `adopt_pid`, `True` after. They are adopted as they appear, and the pool stops
  itself through a shutdown hook that runs before anything is signalled.
- `kill_all` is serialised and idempotent. Several paths can quit at once, and the loser used to
  find the child list already emptied, report “stopped 0”, and let the process exit while the
  winner was still waiting on `terminate`.
- The self-update successor is spawned inside `no_adopt()`. It was going through the patched
  `Popen` and landing in the *dying* instance’s `KILL_ON_JOB_CLOSE` job, so Windows killed the new
  build about a second after it started. Breakaway is not the answer — it needs `BREAKAWAY_OK`,
  which this job deliberately lacks.
- Job adoption failures are no longer swallowed. Silence there is expensive: the guarantee is void
  while everything still looks fine.

**Test:** start a `.pbf` bake, Quit mid-bake. The tray icon should persist saying “stopping”, the
process should exit within seconds, and no `Meld.exe` should remain. `[meld] shutting down…`
should appear once.

### 5. `2b5815d` — `.pbf` files picked by border, not bounding rectangle

Reported: generating **one** cell in Germany baked **two** countries and took ~13.7 minutes.

`select_pbfs` compared the `.pbf` header bbox against the region. A country’s header box is its
bounding *rectangle* — France’s reaches well into Germany even though its border does not. Once
selected, the whole file is streamed.

Geofabrik publishes the real cutting polygon and this module already depends on it for
suggestions, so the honest test was free. Selection rejects on the rectangle first (cheap, clears
most of a folder), then confirms against the polygon.

**The polygon test is exact, not sampled.** Sampling is unsafe in precisely the case that matters:
a country entering the box as a strip narrower than the sample spacing scores zero hits and the
extract is dropped — and dropping an extract is a hole in somebody’s world. Vertex-in-box,
box-corner-in-polygon, and a Liang-Barsky edge crossing cover every way a simple polygon and a
rectangle can meet. `test_bake_plan.py` pins the sliver case specifically.

**Unknown always means keep**, everywhere: unrecognised filename, hand-cut extract, unreadable
header, unreachable index, any exception.

The two bake entry points had each grown their own copy of the header test, so the parallel path
could re-admit a file the planner had rejected. Both call one predicate now.

Also gives the parallel bake a **heartbeat**. The workers are subprocesses and could not reach the
parent’s logger, so a country `.pbf` produced minutes of silence — most of why a working bake read
as a hang.

**Test:** `pytest tests/test_bake_plan.py` (25 tests). For a live check, point the `.pbf` folder at
a folder holding two neighbouring countries and bake one tile well inside one of them; the log
should skip the neighbour.

### 6. `8637d92` — build height that costs nothing was being charged for

Reported: “clicking extend shoots it up to 22 GB”. The world did not change. The estimate did.

`_mb_per_region` scaled linearly with declared height. That is the wrong variable: the fork emits
sections from the world floor up to the highest one holding content, so **raising the ceiling adds
no sections.** Matched real builds already on disk prove it — same bbox, same scale, differing
only in height flags:

| build | sections/chunk | compressed bytes | region file |
| --- | --- | --- | --- |
| `vanilla` | 24.00 | 1,057 | 4,202,496 |
| `extended` (ceiling lifted) | 24.00 | 1,057 | 4,202,496 |
| `deep` (floor lowered to −160) | 26.11 | 1,161 | 4,202,496 |

The linear model predicted `extended` would be 1.042× bigger. It is byte-identical. On a
mountainous 1:1 selection the old model reached ~47.7 MB/region against a measured 5.6.

The model is now a content term × the things that genuinely thicken every section, **plus an
additive term for sections below the vanilla floor**, floored at what an `.mca` physically cannot
go under. Every constant measured, not reasoned:

| constant | value | how |
| --- | --- | --- |
| bake lighting | **1.61×** (was 1.35) | one real region resimulated both ways: 7.344 MiB lit, 4.566 MiB unlit |
| extra all-air section | 52.3 B/chunk baked, 3.9 B unbaked | real `.mca`, k = 1…128 |
| fill fraction | 2.11 of 6 | the `deep` build |
| sector floor | 1024×4096 + 8192 B | 481 of 2,396 real region files sit exactly on it |

The old 1.35 came from “8 KB of light per section before compression”, which is the wrong frame —
uniform light arrays are the *most* compressible payload in a section, not the least
(`zlib(2048 zero bytes)` is 24 bytes).

Same linear term removed from the JS time estimate, for the same reason.

Fixes a latent bug in the floor fit: `settings.get("world_min_y")` returns `None` when unset, and
`str(None)` is `"None"`, not `""` — so the blank test took the explicit-floor branch and threw on
`int(None)`, silently hiding the one case that does cost bytes.

Also warns below **cell size 4**. Each cell builds a `(size+2)²` halo and discards the surplus:
11% useful at size 1, 44% at 4, 56% at 6. Corpus-wide, **343.6M chunks written against 128.9M
kept.** A 2-hour benchmark had been run at size 1 by hand with nothing to say what it cost.

And `write_world_meta` is throttled in the merge path — it re-serialises the whole project dict,
which meant 13,092 times in one run, inside the merge critical section, for a file recording
provenance rather than progress.

**Test:** toggle Extend build height on a mountainous selection. The estimate should barely move.
Set cell size to 1; a modal should offer 4 instead.

### 7. `4e266be` — a calibrated project kept responding to its settings

`_mb_per_region` short-circuited on `mb_per_region_observed` and returned it unchanged. A
measurement beats a model, but it was a measurement of *one* configuration — so once a project had
built anything, turning caves or baked lighting on left the estimate exactly where it was.

A run now records what the model said for the settings it was measured under, and a past
observation is carried across by the ratio the model puts on the change. Projects calibrated
before this existed have no baseline and keep the old behaviour rather than having a ratio
invented for them.

The reports were also missing most of what the models key on — not one on disk recorded caves, the
height flags, land cover or the seam buffer. Cheap to record, impossible to backfill.

## What is in the Arnis fork branch

### `63d74825` — Overture surviving a stale release pointer

Across all 19,018 cell logs: 6,420 Overture fetches, 5,959 succeeded, **16 failed outright** — all
sixteen in the same render, all with

```
STAC catalog download failed with status 404 Not Found
(url: https://stac.overturemaps.org/2026-05-20.0/collections.parquet)
```

Not a slope but a cliff: Overture keeps only the newest few releases online, so when the pointer
goes stale it is stale for every cell at once.

Three changes, none of which alter a working fetch:

- **A cached index that is merely old is now preferred to no index at all.** The refresh window is
  a week; the partitions it points at outlive that comfortably. Previously a failed refresh
  propagated with `?` and the whole Overture step died while a usable index sat on disk unread.
  This alone would have saved all 16 cells.
- **The release that last worked is remembered** next to the cache and tried before the
  compile-time constant. That constant is a date, and dates rot — the bucket currently holds
  exactly two releases, of which the pin is the older.
- Attempts 3 → 4, so discovery still gets two candidates.

### `4a4eced7` — the Bake lighting checkbox has never done anything

`gui_start_generation` takes `bake_lighting_enabled`, the front end has always sent it, and the
`Args` it builds then set `bake_lighting: false` unconditionally. The desktop GUI could not
produce a pre-lit world however the toggle was set. Upstream wires it; this fork stopped, and
`#[allow(unused_variables)]` on the function suppressed exactly the warning that would have said
so. Wired, and the allow removed — it builds clean without it.

## Deliberately not done

Each of these was in the plan and is being left out on purpose, not forgotten.

| Item | Why |
| --- | --- |
| Cells into a non-interactive Leaflet pane | Silently kills click-to-regenerate; must ship with a replacement map-level click handler. The **Show cells** toggle solves the same user problem at a fraction of the risk. |
| Drag the selection rectangle body | leaflet-draw already owns `mousedown` on the rectangle; a hand-rolled `mousemove` fights it. Worth doing with its own transform, not worth bundling. |
| Reaping orphans on next start | With the Quit hang fixed they should stop being created, and a predicate that cannot tell an orphan from the user’s second Meld window is worse than the problem. |
| Batching `set_cell_status` writes | Crash recovery depends on `grid.json` being current. Real cost, but not worth trading resume correctness for. |
| `--write-region-bounds` in the fork | **The single largest measured waste in the app** — 62.5% of every chunk ever written here was generated and discarded. Also the riskiest: it rewrites region-bound derivation in `java.rs`, the same file the B_Linear work landed in. Needs a golden-hash gate and a live render check. Should be its own branch. |
| Full calibration ring buffer + rolling median | The single-observation scaling in `4e266be` gets most of the benefit. The ring buffer wants a shape key and a minimum sample size, which is a design conversation, not a patch. |

Before merging, re-run the dry-run rather than trusting this document:

```
git merge-tree $(git merge-base main HEAD) main HEAD
```

If `feat/gpu-void-naming` has merged to `main` in the meantime, re-check: at the time of writing
it touched only `src/caves/mod.rs` and two docs files in the fork, with **no overlap** with either

### What has NOT been tested

No live end-to-end render has been run against these branches. The Python suite, `cargo check`,
the JS parse and several targeted process-level experiments all pass, but **a real multi-cell
generation should be run before release**, particularly for:

- the Quit path mid-bake (Phase 4 changes process teardown)
- a `.pbf` bake against a real multi-country folder (Phase 5 changes which data is read)
- an Overture fetch against a cold cache (fork branch changes the resolve path)
